# MILESTONES — מחולל בדיחות מבוסס AI

מסמך זה מגדיר אבני דרך לפיתוח בהתאם ל־`PRD.md`, `ARCHITECTURE.md` ו־`DESIGN.md`. סדר הפיתוח מחייב, וכל אבן דרך תיבדק ותאושר בפני עצמה. המסך היחיד למימוש הוא **מסך יצירת בדיחה**; מסך "אודות" שמופיע בתמונת Mockups אינו חלק מהיקף המוצר.

## Milestone 1 — הקמת הפרויקט וסביבת בדיקה זמינה ✅

**מטרה:** להעמיד בסיס פיתוח תקין, עם מסך ראשי נגיש בדפדפן ו־Preview Deployment שאפשר לפתוח ולבדוק, לפני שילוב AI.

**מה יש לממש:**
- יצירת Repository יחיד ב־GitHub לפרויקט Next.js App Router ו־TypeScript; הגדרת פקודות Build, בדיקת טיפוסים ו־Lint, וכן `.gitignore` המונע העלאת Secrets.
- הקמת המסך היחיד במבנה בסיסי התואם ל־Wireframes: כותרת בעברית, שדה נושא וכפתור "צור בדיחה"; בשלב זה אין לטעון שיצירת בדיחה פועלת ואין להציג תוכן מדומה כתוצאה אמיתית.
- הגדרת `lang="he"`, `dir="rtl"` והתאמה ראשונית ל־Mobile.
- חיבור ה־Repository ל־Vercel והפעלת Preview Deployment אוטומטי לענף פיתוח / Pull Request.

**תוצר מצופה:** קישור Preview פעיל שבו ניתן לראות את מסך הבסיס בעברית; טרם נשלחות בקשות GPT-5.

**Definition of Done:**
- הקוד נמצא ב־GitHub; Build, TypeScript ו־Lint עוברים ללא שגיאות.
- מסך הבית נטען ב־Preview, מותאם לרוחב Smartphone ומוצג ב־RTL ללא גלילה אופקית.
- Push/PR מעדכן את ה־Preview אוטומטית, ללא Deployment ידני.
- אין Secrets בקוד, ב־Repository או ב־Client bundle.
- הוצג למשתמש URL פעיל לבדיקת המסך הבסיסי, תוך ציון ברור שה־AI עדיין לא מחובר.

## Milestone 2 — יצירת בדיחה עובדת מקצה לקצה

**מטרה:** לממש את יכולת הליבה: המשתמש מזין נושא או משאיר אותו ריק ומקבל בדיחה אמיתית באותו מסך.

**מה יש לממש:**
- שדה נושא עם מגבלה של 100 תווים והפעלת "צור בדיחה"; אזור תוצאה יחיד מתחת לקלט.
- `POST /api/jokes` באמצעות Next.js Route Handler ב־Node.js, עם אימות JSON, טיפוס ואורך נושא וגודל בקשה; החזרת תגובת JSON מוסכמת.
- פנייה ל־GPT-5 באמצעות OpenAI Responses API ו־SDK רשמי **אך ורק ב־Backend**; מפתח `OPENAI_API_KEY` ב־Environment Variables של סביבת הפיתוח/Preview, ללא חשיפה ל־Frontend. שימוש ב־`store: false`.
- הוראות יצירה לפי ה־PRD: נושא בעברית → בדיחה בעברית; נושא באנגלית → בדיחה באנגלית; נושא ריק → בדיחה כללית בעברית; סגנון ואורך גמישים.
- חיווי בזמן ההמתנה, והצגת בדיחה אחת בלבד; תוצאה חדשה מחליפה את הקודמת רק לאחר הצלחה. אין היסטוריה או אחסון מתמשך.

**תוצר מצופה:** יכולת עובדת ב־Preview ליצירת בדיחה אמיתית לפי נושא, או בדיחה כללית ללא נושא.

**Definition of Done:**
- יצירה בנושא "חתולים" מחזירה בדיחה בנושא בעברית, ונושא באנגלית מחזיר בדיחה באנגלית בבדיקות ידניות; שדה ריק מחזיר בדיחה כללית בעברית. תוצאות GPT-5 משתנות ואינן נבדקות באמצעות התאמת טקסט קבוע.
- בקשה תקינה מחזירה `200` עם `joke` שאינו ריק; בקשות עם טיפוס שגוי, JSON פגום או נושא מעל 100 תווים נדחות לפני קריאה ל־OpenAI; גודל Body חריג נדחה.
- הממשק מגביל קלט ל־100 תווים, מציג טעינה ותוצאה באותו מסך, ואינו מציג יותר מבדיחה אחת.
- OpenAI API אינו נקרא מהדפדפן, והמפתח אינו מופיע בתעבורת Client, ב־Build או בלוגים.
- רענון העמוד מוחק את הבדיחה; לא נוצרו Database, שמירת בדיחות או חשבונות משתמשים.
- הבדיקות וה־Build עוברים וה־Preview מאפשר בדיקה עצמאית של התהליך.

## Milestone 3 — חוויית שימוש מלאה ועיצוב

**מטרה:** להשלים את יכולות המשתמש וההופעה החזותית של המסך האחד בהתאם ל־DESIGN, בלי לשנות את הזרימה הקיימת.

**מה יש לממש:**
- כפתור "בדיחה נוספת" המבקש בדיחה לפי **הנושא של הבדיחה האחרונה שנוצרה בהצלחה**, גם לאחר עריכת שדה הנושא; החלפת תוצאה רק בהצלחה.
- כפתור "העתק בדיחה" המשתמש ב־Clipboard API להעתקת הטקסט המוצג; טיפול בהעתקה שנכשלה.
- מצב Client בזיכרון העמוד בלבד (`draftTopic`, `displayedJoke`, `lastSuccessfulTopic`, מצב בקשה); מניעת בקשות יצירה חופפות ושימור הבדיחה הקודמת בזמן עריכת נושא או כישלון.
- מימוש המסך היחיד לפי סדר ה־Wireframes והשפה העיצובית של Style Guide/Mockups: צבעי Comic/Pop Art, Typography עברית, כפתורים, שדה וכרטיס בדיחה; התאמה ל־RTL ולטקסט בדיחה באנגלית ב־LTR; גלילה לתוכן ארוך.

**תוצר מצופה:** מסך מעוצב ופונקציונלי במלואו ב־Preview, שבו ניתן להחליף נושא, לקבל בדיחה נוספת ולהעתיק את הבדיחה.

**Definition of Done:**
- לאחר יצירת בדיחה בנושא א', שינוי שדה הנושא לב' אינו מוחק את התוצאה; "בדיחה נוספת" משתמש עדיין בא', ו"צור בדיחה" משתמש בב'. לאחר הצלחת יצירה בב', "בדיחה נוספת" משתמש בב'.
- כפתור ההעתקה מעתיק במדויק את הבדיחה המוצגת; כישלון הרשאת Clipboard אינו גורם לקריסת המסך.
- לחיצות מהירות אינן יוצרות בקשות יצירה חופפות או תוצאה ישנה הדורסת תוצאה חדשה.
- במובייל, כותרת, קלט, פעולות וכרטיס מוצגים בסדר שנקבע ב־DESIGN; הטקסט קריא, אין גלילה אופקית, וניווט מקלדת וקריאת התוצאה ב־Screen Reader נבדקו.
- תוכן באנגלית מוצג בכיווניות מתאימה בעוד טקסטי הממשק נשארים בעברית.
- אין מסך "אודות", תפריטים, שיתוף מובנה או פיצ'רים נוספים שאינם ב־PRD.

## Milestone 4 — עמידות, Rate Limiting ו־PWA

**מטרה:** להפוך את התהליך השלם לאמין יותר, להגביל שימוש מוגזם ולאפשר התקנת האפליקציה במכשירים תומכים.

**מה יש לממש:**
- ניסיון חוזר אוטומטי אחד ב־Backend בלבד עבור שגיאת OpenAI זמנית; ביטול Retry מובנה ב־SDK והגדרת Timeout התואם למגבלת Function. שגיאות קלט ואימות/הרשאות לא יגררו Retry.
- טיפול בהודעות שגיאה בעברית, כולל `429`, היעדר רשת, תגובה לא תקינה וכישלון לאחר ניסיון חוזר. הבדיחה האחרונה תישאר מוצגת אם יצירה חדשה נכשלת.
- הגדרת **Vercel WAF Rate Limiting** במסלול `/api/jokes`: עד **5 בקשות ב־60 שניות לפי IP**, עם חסימה ב־HTTP `429` לפני הפעלת AI. זוהי מגבלת IP כקירוב למשתמש אנונימי, ולא זיהוי אישי מובטח. לבדוק את המדיניות בסביבת Vercel הרלוונטית, ולא להניח שההגדרה נמצאת ב־Git.
- הגדרת PWA Manifest, שם בעברית, `display: standalone`, אייקונים ו־HTTPS; ללא Service Worker ל־Offline caching וללא יכולת יצירת בדיחות ללא אינטרנט.

**תוצר מצופה:** Preview מוגן ומוכן להתקנה כ־PWA, עם טיפול בכשלים ומגבלת בקשות מאומתת.

**Definition of Done:**
- סימולציה של כשל OpenAI זמני מוכיחה שלכל בקשת יצירה נעשות לכל היותר **שתי** קריאות OpenAI, ושהתוצאה או הודעת השגיאה מטופלות בהתאם; כשל שאינו בר־חזרה אינו מפעיל ניסיון נוסף.
- במקרה של Timeout/כשל, מופיעה הודעה בעברית, לא נחשף מידע פנימי והבדיחה הישנה נשמרת.
- בדיקת שש בקשות בתקופת 60 שניות מאותו IP בסביבה שבה ה־WAF פעיל מראה שהבקשה השישית נחסמת ב־429 **לפני** OpenAI, ומוצגת הודעה בעברית. הבדיקה מתייחסת לבקשות לנתיב API, לא למספר ניסיונות פנימיים של OpenAI.
- Manifest ואייקונים נבדקים; במכשיר/דפדפן תומך ניתן להתקין ולהפעיל כ־PWA. ללא רשת אין הבטחה להפעלת האפליקציה או ליצירת בדיחה.
- לא נוספו Database, Auth, Local Storage או שמירת היסטוריה.

## Milestone 5 — בדיקות קבלה ופריסה ל־Production

**מטרה:** לפרסם גרסה מלאה, מאובטחת וניתנת לבדיקה באתר החי, עם תהליך עדכון אוטומטי מ־GitHub.

**מה יש לממש:**
- הגדרת סביבות Vercel Preview ו־Production עם `OPENAI_API_KEY` נפרד לכל סביבה ככל שזמין; שמירת Secret של Production **רק** ב־Vercel Production, ללא פרסומו בקוד. התאמת Timeout/Function והגנות Header נדרשות.
- הגדרת כלל WAF ב־Production ואימות אכיפתו בפועל; בחינת הרשאות ותוכנית Vercel המתאימה לשימוש המתוכנן, ומגבלות/בקרות הוצאה בחשבון OpenAI.
- ביצוע בדיקות קבלה במכשיר מובייל ובדפדפן, לרבות יצירה בעברית ובאנגלית, נושא ריק, בדיחה נוספת, העתקה, שגיאות, מגבלת קצב, רענון והתקנת PWA.
- ביצוע Merge לענף `main` לאחר אישור המשתמש, והפעלת Production Deployment אוטומטי דרך חיבור Vercel–GitHub; אימות התוצאה באתר החי.

**תוצר מצופה:** אתר Production פעיל ב־HTTPS, עם מסך יצירת בדיחה אחד, PWA ומנגנוני ההגנה שנבדקו, ויכולת Deployment אוטומטי לעדכונים מאושרים.

**Definition of Done:**
- כל הבדיקות הפונקציונליות והחזותיות שנקבעו באבני הדרך הקודמות עוברות גם ב־Production, כולל בדיקת WAF ממשית מול `/api/jokes`.
- מפתח ה־API נשמר בצד השרת בלבד; מפתח Production אינו נכלל ב־Repository, ב־Client bundle או בסביבת הפיתוח המקומית.
- Production מקבל Build תקין מ־`main` ללא Deployment ידני; ניתן לזהות את גרסת הקוד שנפרסה וידוע כיצד לבצע Rollback דרך Vercel.
- האתר נפתח ב־HTTPS בטלפון, עובד מחיבור אינטרנט וניתן להתקנה כ־PWA במכשיר תומך.
- אימות סופי: אין מסד נתונים, חשבונות, היסטוריה, מסכים נוספים או פעילות Offline שנוספו שלא בהתאם ל־PRD.
- הוצגו למשתמש קישור Production, תוצאות בדיקות הקבלה, כל מגבלה שנותרה, והתקבל אישור מפורש לסיום אבן הדרך.

## Development Execution Rules — הנחיות מחייבות ל־AI המבצע

1. **יש לפתח את ה־Milestones לפי סדר הופעתם במסמך.** מותר להכין תשתית מינימלית הנדרשת לאבן הדרך הנוכחית, אך אין להתחיל לממש יכולות של אבן דרך מאוחרת ללא אישור.
2. **בסיום כל Milestone יש לעצור את הפיתוח** ולהציג למשתמש תוצר עובד ונגיש לבדיקה (למשל URL של Preview או Production), סיכום קצר של מה שמומש, ותוצאות בדיקות מול כל סעיפי ה־Definition of Done; יש להציג במפורש סעיפים שלא עברו או שלא ניתן היה לבדוק.
3. **אין להתחיל לפתח את ה־Milestone הבא לפני אישור מפורש של המשתמש.** אין להתייחס להשלמת Build או ל־Deployment אוטומטי כתחליף לאישור.
4. בהפעלת שירות חיצוני הדורש פעולה מצד המשתמש, יש להדריך אותו בשפה פשוטה ולבקש את הפעולה הדרושה, בלי לבקש ממנו לשתף Secret בצ'אט או להעלות אותו ל־GitHub.
5. במקרה של סתירה בין המקורות: `PRD.md` קובע היקף והתנהגות; `ARCHITECTURE.md` קובע מימוש טכני; `DESIGN.md` קובע מראה ופריסה תוך שמירה על קדימות ה־Wireframes למבנה. אין להוסיף יכולות כדי לפתור סתירה ללא אישור המשתמש.

**הערה:** אין בפרויקט Database ולכן אין צורך בפרויקטי Supabase, סביבת Database Development/Production או Database Migrations.
